# 集群配置步骤

在本指南中，我们将配置 Kubernetes 集群，用于使用 Triton Server 和 TRT-LLM 部署 LLM。
*
## 1. 添加节点标签和污点

第一步是添加节点标签（label）和污点（taint）

* 节点标签 `nvidia.com/gpu=present`，用于更方便地识别带有 NVIDIA GPU 的节点。
* 节点污点 `nvidia.com/gpu=present:NoSchedule`，用于阻止非 GPU 的 Pod 被调度到 GPU 节点上。

运行以下命令查看节点：

```
kubectl get nodes
```

你应该会看到类似下面的输出：

```
NAME                          STATUS   ROLES    AGE     VERSION
ip-192-168-117-30.ec2.internal   Ready    <none>   3h10m   v1.30.2-eks-1552ad0
ip-192-168-127-31.ec2.internal   Ready    <none>   155m    v1.30.2-eks-1552ad0
ip-192-168-26-106.ec2.internal   Ready    <none>   3h23m   v1.30.2-eks-1552ad0
```

> [!Note]
> 这里我们有 3 个节点：1 个 CPU 节点和 2 个 GPU 节点。你只需要对 GPU 节点应用标签和污点。注意，由于 GPU 节点启用了 EFA，它们必须位于 VPC 的同一子网中，因此它们的 IP 地址比较接近。在本例中，最上面的 2 个节点很可能就是 GPU 节点。你也可以运行 `kubectl describe node <node_name>` 来确认。

运行以下命令添加标签和污点：

```
kubectl label nodes ip-192-168-117-30.ec2.internal nvidia.com/gpu=present
kubectl label nodes ip-192-168-127-31.ec2.internal nvidia.com/gpu=present
kubectl taint nodes ip-192-168-117-30.ec2.internal nvidia.com/gpu=present:NoSchedule
kubectl taint nodes ip-192-168-127-31.ec2.internal nvidia.com/gpu=present:NoSchedule
```

或者，你也可以在 [EKS 控制台](https://console.aws.amazon.com/eks/home) 的节点组中配置标签和污点。

> 💡 **AI Infra 视角**：标签 + 污点 + 容忍是 Kubernetes 中"资源隔离"的经典组合。污点（taint）是打在节点上的"排斥标记"，只有声明了对应容忍（toleration）的 Pod 才被允许调度上来。这里用 `NoSchedule` 污点把 GPU 节点保护起来，避免普通业务 Pod 抢占 GPU 资源；而需要 GPU 的服务（Triton、DCGM Exporter 等）则通过 tolerations 显式声明"我愿意接受这个污点"。这套机制在混合负载的推理集群里几乎是标配。

## 2. 安装 Kubernetes Node Feature Discovery 服务

它允许 Pod 被调度到带有我们上面设置的匹配污点的节点上。

```
kubectl create namespace monitoring
helm repo add kube-nfd https://kubernetes-sigs.github.io/node-feature-discovery/charts && helm repo update
helm install -n kube-system node-feature-discovery kube-nfd/node-feature-discovery \
  --set nameOverride=node-feature-discovery \
  --set worker.tolerations[0].key=nvidia.com/gpu \
  --set worker.tolerations[0].operator=Exists \
  --set worker.tolerations[0].effect=NoSchedule
```

## 3. 安装 NVIDIA Device Plugin

我们在这里使用 NVIDIA Device Plugin，是因为默认的 EKS 优化 AMI（Amazon Linux 2）已经预装了 NVIDIA 驱动。如果你想使用未预装驱动的 EKS Ubuntu AMI，则需要改用 [NVIDIA GPU Operator](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/amazon-eks.html#nvidia-gpu-operator-with-amazon-eks) 方案。

```
kubectl create -f https://raw.githubusercontent.com/NVIDIA/k8s-device-plugin/v0.15.0/deployments/static/nvidia-device-plugin.yml
```

> 💡 **AI Infra 视角**：NVIDIA Device Plugin 以 DaemonSet 形式在每个节点上运行，它的职责是把节点的 GPU 数量上报给 kubelet，让 GPU 成为 Kubernetes 调度器可感知的"可调度资源"（`nvidia.com/gpu`）。Pod 在 resources 里声明 `nvidia.com/gpu: 4`，调度器就能据此找到有足够 GPU 的节点——没有它，Kubernetes 根本不知道节点上有 GPU，也就无法为 GPU 工作负载调度。这是理解"GPU 在 K8s 中的调度"最核心的一环：K8s 本身不认 GPU，全靠设备插件把硬件抽象成资源。

## 4. 安装 NVIDIA GPU Feature Discovery 服务

```
cd multinode_helm_chart/
kubectl apply -f nvidia_gpu-feature-discovery_daemonset.yaml
```

> 💡 **AI Infra 视角**：GPU Feature Discovery 解决的是"GPU 同质化"问题——默认情况下 K8s 把所有 GPU 都看成同一个资源 `nvidia.com/gpu`，无法区分 A10G 和 H100。GFD 自动检测节点上 GPU 的型号、显存等特性并打成节点标签（如 `nvidia.com/gpu.product`），这样部署时就能通过 nodeSelector 指定"只调度到有 H100 的节点上"。对混合 GPU 机型（mixed SKU）的集群来说，这个组件几乎是必须的。

## 5. 安装 Prometheus Kubernetes Stack

Prometheus Kubernetes Stack 会安装指标采集所需的各种组件，包括 Prometheus、Kube-State-Metrics、Grafana 等。

```
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts && helm repo update
helm install -n monitoring prometheus prometheus-community/kube-prometheus-stack \
  --set tolerations[0].key=nvidia.com/gpu \
  --set tolerations[0].operator=Exists \
  --set tolerations[0].effect=NoSchedule
```

## 6. 安装 NVIDIA DCGM Exporter

这个 exporter 让我们能够通过 DCGM 采集 GPU 指标，这也是在集群中监控 GPU 状态的推荐方式。

```
helm repo add nvidia-dcgm https://nvidia.github.io/dcgm-exporter/helm-charts && helm repo update
helm install -n monitoring dcgm-exporter nvidia-dcgm/dcgm-exporter --values nvidia_dcgm-exporter_values.yaml
```

你可以通过展示 DCGM 采集到的指标来验证安装：

```
kubectl -n monitoring port-forward svc/dcgm-exporter 8080:9400
```

在本地浏览器中，你应该能在 `localhost:8080` 看到指标。

## 7. 安装 Prometheus Adapter

它让 Prometheus 服务器采集到的 Triton 指标能够被 Kubernetes 的 Horizontal Pod Autoscaler 服务使用。

```
helm install -n monitoring prometheus-adapter prometheus-community/prometheus-adapter \
  --set metricsRelistInterval=6s \
  --set customLabels.monitoring=prometheus-adapter \
  --set customLabels.release=prometheus \
  --set prometheus.url=http://prometheus-kube-prometheus-prometheus \
  --set additionalLabels.release=prometheus
```

要验证 Prometheus Adapter 是否正常工作，运行以下命令：

```
kubectl get --raw /apis/custom.metrics.k8s.io/v1beta1
```

如果命令失败，请多等一会儿再重试。如果连续几分钟都失败，说明 adapter 配置有误，需要人工干预。

> 💡 **AI Infra 视角**：HPA 默认只能读 CPU/内存这类内置指标，而推理服务最该参考的是"队列积压"这类业务指标。Prometheus Adapter 的作用就是把 Prometheus 里存的自定义指标通过 `custom.metrics.k8s.io` API 暴露给 HPA，相当于给 K8s 扩展了一套"指标接口"。这条链路（Triton 指标 → Prometheus → Adapter → HPA）就是生产环境基于业务指标做弹性伸缩的标准路径。相比之下，KEDA 是另一条更现代的思路，它把伸缩触发器和事件源解耦，但基本原理一致。

## 8. 安装 Triton 指标相关的 Prometheus rule

它会基于 Prometheus 采集到的 Triton 指标，通过公式生成自定义指标。其中有一个自定义指标用于 Horizontal Pod Autoscaler（HPA）。用户可以修改这个 manifest，创建自己的自定义指标，并在 HPA manifest 中引用它们。

```
kubectl apply -f triton-metrics_prometheus-rule.yaml
```

至此，所有指标组件应该都已安装完成。现在，包括 Triton 指标、DCGM 指标和自定义指标在内的所有指标都应该已经对 Prometheus 服务器可用。你可以通过展示 Prometheus 服务器中的所有指标来验证：

```
kubectl -n monitoring port-forward svc/prometheus-kube-prometheus-prometheus 8080:9090
```

在本地浏览器中，你应该能在 `localhost:8080` 看到上面提到的所有指标。

## 9. 安装 EFA Kubernetes Device Plugin

拉取 EFA Kubernetes Device Plugin 的 helm chart：

```
helm repo add eks https://aws.github.io/eks-charts
helm pull eks/aws-efa-k8s-device-plugin --untar
```

在 `aws-efa-k8s-device-plugin/values.yaml` 的第 134 行附近添加如下容忍（tolerations）：

```
tolerations:
- key: nvidia.com/gpu
  operator: Exists
  effect: NoSchedule
```

安装 EFA Kubernetes Device Plugin 的 helm chart：

```
helm install aws-efa-k8s-device-plugin --namespace kube-system ./aws-efa-k8s-device-plugin/
```

> 💡 **AI Infra 视角**：EFA（Elastic Fabric Adapter）是 AWS 专为高性能计算设计的网络接口，提供 RDMA 能力，能让 GPU 之间绕过 CPU 直接做内存访问（GPUDirect RDMA）。对跨节点的张量并行（tensor parallelism）来说，每一层都要做 AllReduce 同步，通信延迟直接决定推理吞吐，EFA 因此成了 AWS 上多节点 LLM 推理/训练的标配。设备插件负责把 EFA 资源注册给 K8s 调度器，Pod 里声明 `vpc.amazonaws.com/efa: 1` 即可申请。

## 10. 安装 Cluster Autoscaler

> [!Note]
> - 需要先挂载 Autoscaler 的 IAM add-on 策略（如果使用示例配置创建 EKS 集群，这一步已完成）。
> - Cluster Autoscaler 不会超出你在节点组中设置的最大节点数。所以如果希望 Cluster Autoscaler 能向节点组添加更多节点，请相应设置好最大节点数。
> - Cluster Autoscaler 只在存在 `unschedulable`（无法调度）的 Pod 时才增加节点数；当新增节点变"空闲"时，它也会缩减节点。

### a. 部署 Cluster Autoscaler 的 deployment

```
kubectl apply -f https://raw.githubusercontent.com/kubernetes/autoscaler/master/cluster-autoscaler/cloudprovider/aws/examples/cluster-autoscaler-autodiscover.yaml
```

### b. 设置镜像版本

这里我们把镜像版本设为 `v1.30.2`，请确保它与你 EKS 集群的版本一致。

```
kubectl -n kube-system set image deployment.apps/cluster-autoscaler cluster-autoscaler=registry.k8s.io/autoscaling/cluster-autoscaler:v1.30.2
```

### c. 为 deployment 添加所需的 safe-to-evict 注解

```
kubectl -n kube-system annotate deployment.apps/cluster-autoscaler cluster-autoscaler.kubernetes.io/safe-to-evict="false"
```

### d. 编辑 manifest 文件

```
kubectl -n kube-system edit deployment.apps/cluster-autoscaler

# Change 1: Add your cluster name:
- --node-group-auto-discovery=asg:tag=k8s.io/cluster-autoscaler/enabled,k8s.io/cluster-autoscaler/<your_cluster_name>

# Change 2: Add the following two lines below the line above:
- --balance-similar-node-groups
- --skip-nodes-with-system-pods=false
```

## 11. 安装 LeaderWorkerSet

这让我们可以使用 LeaderWorkerSet API 进行多节点 Triton 部署。

```
VERSION=v0.3.0
kubectl apply --server-side -f https://github.com/kubernetes-sigs/lws/releases/download/$VERSION/manifests.yaml
```
