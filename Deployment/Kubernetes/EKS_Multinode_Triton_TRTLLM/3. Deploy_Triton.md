# 在 EKS 集群上使用 Triton + TRT-LLM 部署多节点 LLM 的步骤

## 1. 构建自定义容器镜像并推送到 Amazon ECR

我们需要在 Triton TRT-LLM NGC 容器之上构建自定义镜像，把 kubessh 文件、server.py 以及其他 EFA 库打进去，然后将镜像推送到 Amazon ECR。你可以在这里查看 [Dockerfile](https://github.com/Wenhan-Tan/EKS_Multinode_Triton_TRTLLM/blob/main/multinode_helm_chart/containers/triton_trt_llm.containerfile)。

```
## AWS
export AWS_REGION=us-east-1
export ACCOUNT=$(aws sts get-caller-identity --query Account --output text)

## Docker Image
export REGISTRY=${ACCOUNT}.dkr.ecr.${AWS_REGION}.amazonaws.com/
export IMAGE=triton_trtllm_multinode
export TAG=":24.07"

docker build \
  --file ./triton_trt_llm.containerfile \
  --rm \
  --tag ${REGISTRY}${IMAGE}${TAG} \
  .

echo "Logging in to $REGISTRY ..."
aws ecr get-login-password | docker login --username AWS --password-stdin $REGISTRY

# Create registry if it does not exist
REGISTRY_COUNT=$(aws ecr describe-repositories | grep ${IMAGE} | wc -l)
if [ "$REGISTRY_COUNT" == "0" ]; then
        echo ""
        echo "Creating repository ${IMAGE} ..."
        aws ecr create-repository --repository-name ${IMAGE}
fi

# Push image
docker image push ${REGISTRY}${IMAGE}${TAG}
```

## 2. 为 LLM 部署准备 Triton 模型仓库

要在计算节点内构建 TRT-LLM 引擎并配置 Triton 模型仓库，请按以下步骤操作：

### a. 修改 `setup_ssh_efs.yaml` 文件

我们使用 `setup_ssh_efs.yaml` 文件（其执行"sleep infinity"）在计算节点内配置 ssh 访问并挂载 EFS。

需要调整以下值：

- `image`：修改镜像标签。默认是 24.07，支持 TRT-LLM v0.11.0
- `nvidia.com/gpu`：设为集群中每个节点的 GPU 数量，在 limits 和 requests 两处都要修改
- `claimName`：设为你的 EFS pvc 名称

### b. SSH 进入计算节点并构建 TRT-LLM 引擎

部署 Pod：

```
cd multinode_helm_chart/
kubectl apply -f setup_ssh_efs.yaml
kubectl exec -it setup_ssh_efs -- bash
```

克隆 Triton TRT-LLM 后端仓库：

```
cd <EFS_mount_path>
git clone https://github.com/triton-inference-server/tensorrtllm_backend.git -b v0.11.0
cd tensorrtllm_backend
git lfs install
git submodule update --init --recursive
```

构建一个 Llama3-8B 引擎，张量并行度（Tensor Parallelism）=4，流水线并行度（Pipeline Parallelism）=2，运行在 2 个 g5.12xlarge 节点上（每个节点 4 块 A10G GPU），总计跨 2 个节点的 8 块 GPU。

```
cd tensorrtllm_backend/tensorrt_llm/examples/llama
git clone https://huggingface.co/meta-llama/Meta-Llama-3-8B

python convert_checkpoint.py --model_dir ./Meta-Llama-3-8B \
                             --output_dir ./converted_checkpoint \
                             --dtype float16 \
                             --tp_size 4 \
                             --pp_size 2

trtllm-build --checkpoint_dir ./converted_checkpoint \
             --output_dir ./output_engines \
             --gemm_plugin float16 \
             --use_custom_all_reduce disable \ # only disable on non-NVLink machines like g5.12xlarge
             --max_input_len 2048 \
             --max_output_len 2048 \
             --max_batch_size 4
```

> 💡 **AI Infra 视角**：这里 TP=4、PP=2 是理解分布式推理并行度的关键示例。张量并行（tensor parallelism）把每一层切分到多块 GPU 上，单次前向计算需要一次跨 GPU 的 AllReduce 通信，因此对节点间带宽极其敏感，通常只跨 NVLink 或 EFA 使用；流水线并行（pipeline parallelism）则按层分段，通信量小得多但存在流水线气泡（bubble）。总 GPU 数 = TP × PP = 8，正好对应 2 个节点 × 4 块 GPU。`use_custom_all_reduce disable` 是因为 g5.12xlarge 没有 NVLink，跨节点通信必须走 EFA 上的 NCCL。

### c. 准备 Triton 模型仓库

```
cd <EFS_MOUNT_PATH>/tensorrtllm_backend
mkdir triton_model_repo

cp -r all_models/inflight_batcher_llm/ensemble triton_model_repo/
cp -r all_models/inflight_batcher_llm/preprocessing triton_model_repo/
cp -r all_models/inflight_batcher_llm/postprocessing triton_model_repo/
cp -r all_models/inflight_batcher_llm/tensorrt_llm triton_model_repo/

python3 tools/fill_template.py -i triton_model_repo/preprocessing/config.pbtxt tokenizer_dir:<PATH_TO_TOKENIZER>,tokenizer_type:llama,triton_max_batch_size:4,preprocessing_instance_count:1
python3 tools/fill_template.py -i triton_model_repo/tensorrt_llm/config.pbtxt triton_backend:tensorrtllm,triton_max_batch_size:4,decoupled_mode:True,max_beam_width:1,engine_dir:<PATH_TO_ENGINES>,,enable_kv_cache_reuse:False,batching_strategy:inflight_batching,max_queue_delay_microseconds:0
python3 tools/fill_template.py -i triton_model_repo/postprocessing/config.pbtxt tokenizer_dir:<PATH_TO_TOKENIZER>,tokenizer_type:llama,triton_max_batch_size:4,postprocessing_instance_count:1
python3 tools/fill_template.py -i triton_model_repo/ensemble/config.pbtxt triton_max_batch_size:4
```

> [!Note]
> 请务必把上面示例中的 `<PATH_TO_TOKENIZER>` 和 `<PATH_TO_ENGINES>` 替换成正确的值。请记住，tokenizer、TRT-LLM 引擎和 Triton 模型仓库必须放在节点之间共享的文件存储中，它们是 Triton 启动模型所必需的。例如，如果使用 AWS EFS，`<PATH_TO_TOKENIZER>` 和 `<PATH_TO_ENGINES>` 的值应相对于实际的 EFS 挂载路径，这个路径由你的持久卷声明（persistent-volume claim）和 chart/templates/deployment.yaml 中的挂载路径决定。请确保你的节点能够访问这些文件。

## 3. 创建用于部署的 `example_values.yaml` 文件

请先仔细阅读提供的 `values.yaml`，理解每个值的含义。

下面是我们使用的 `example_values.yaml` 文件，其中 `<EFS_MOUNT_PATH>=/var/run/models`：

```
gpu: NVIDIA-A10G
gpuPerNode: 4
persistentVolumeClaim: efs-claim

tensorrtLLM:
  parallelism:
    tensor: 4
    pipeline: 2

triton:
  image:
    name: wenhant16/triton_trtllm_multinode:24.07.10
    # name: ${ACCOUNT}.dkr.ecr.${AWS_REGION}.amazonaws.com/triton_trtllm_multinode:24.07
  resources:
    cpu: 4
    memory: 64Gi
    efa: 1 # If you don't want to enable EFA, set this to 0.
  triton_model_repo_path: /var/run/models/tensorrtllm_backend/triton_model_repo
  enable_nsys: false # Note if you send lots of requests, nsys report can be very large.

logging:
  tritonServer:
    verbose: False

autoscaling:
  enable: true
  replicas:
    maximum: 2
    minimum: 1
  metric:
    name: triton:queue_compute:ratio
    value: 1
```

## 6. 测试 Horizontal Pod Autoscaler 和 Cluster Autoscaler

查看 HPA 状态，运行：

```
kubectl get hpa multinode_deployment
```

输出应该类似下面这样：

```
NAME                   REFERENCE                                TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
multinode_deployment   LeaderWorkerSet/leaderworkerset-sample   0/1       1         2         1          66m
```

从上面的输出可以看到，当前指标值为 0，目标值为 1。注意在本示例中，我们的指标是在 Prometheus Rule 中定义的自定义指标。更多细节可以参考[安装 Triton 指标相关的 Prometheus rule](./2.%20Configure_EKS_Cluster.md#8-install-prometheus-rule-for-triton-metrics)这一步。当当前值超过 1 时，HPA 就会开始创建新副本。我们可以通过向 LoadBalancer 发送大量请求来增加流量，也可以手动调高最小副本数，让 HPA 创建第二个副本。本示例选择后者，运行以下命令：

```
kubectl patch hpa multinode_deployment -p '{"spec":{"minReplicas": 2}}'
```

此时 `kubectl get pods` 的输出应该类似下面这样：

```
NAME                         READY   STATUS    RESTARTS   AGE
leaderworkerset-sample-0     1/1     Running   0          6h48m
leaderworkerset-sample-0-1   1/1     Running   0          6h48m
leaderworkerset-sample-1     0/1     Pending   0          13s
leaderworkerset-sample-1-1   0/1     Pending   0          13s
```

可以看到第二个副本已经创建，但状态是 `Pending`。如果运行 `kubectl describe pod leaderworkerset-sample-1`，应该能看到类似下面的事件：

```
Events:
  Type     Reason            Age   From                Message
  ----     ------            ----  ----                -------
  Warning  FailedScheduling  48s   default-scheduler   0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 2 Insufficient nvidia.com/gpu, 2 Insufficient vpc.amazonaws.com/efa. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.
  Normal   TriggeredScaleUp  15s   cluster-autoscaler  pod triggered scale-up: [{eks-efa-compute-ng-2-7ac8948c-e79a-9ad8-f27f-70bf073a9bfa 2->4 (max: 4)}]
```

第一个事件说明当前没有可用节点来调度这些 Pod，这也解释了为什么第二个副本的两个 Pod 处于 `Pending` 状态。第二个事件表明 Cluster Autoscaler 检测到这个 Pod 是 `unschedulable`（无法调度的），因此它会增加集群中的节点数，直到达到上限。更多细节可以参考[安装 Cluster Autoscaler](./2.%20Configure_EKS_Cluster.md#10-install-cluster-autoscaler)这一步。这个过程可能需要一些时间，取决于 AWS 是否有足够的节点可供添加到你的集群。最终，Cluster Autoscaler 会在节点组中添加 2 个新节点，让 2 个 `Pending` 的 Pod 得以调度上去。此时 `kubectl get nodes` 和 `kubectl get pods` 的输出应该类似下面这样：

```
NAME                             STATUS   ROLES    AGE   VERSION
ip-192-168-103-11.ec2.internal   Ready    <none>   15m   v1.30.2-eks-1552ad0
ip-192-168-106-8.ec2.internal    Ready    <none>   15m   v1.30.2-eks-1552ad0
ip-192-168-117-30.ec2.internal   Ready    <none>   11h   v1.30.2-eks-1552ad0
ip-192-168-127-31.ec2.internal   Ready    <none>   11h   v1.30.2-eks-1552ad0
ip-192-168-26-106.ec2.internal   Ready    <none>   11h   v1.30.2-eks-1552ad0
```

```
leaderworkerset-sample-0     1/1     Running   0          7h26m
leaderworkerset-sample-0-1   1/1     Running   0          7h26m
leaderworkerset-sample-1     1/1     Running   0          38m
leaderworkerset-sample-1-1   1/1     Running   0          38m
```

你可以运行以下命令把最小副本数改回 1：

```
kubectl patch hpa multinode_deployment -p '{"spec":{"minReplicas": 1}}'
```

如果当前指标没有超过目标值，HPA 会删除第二个副本。当 Cluster Autoscaler 检测到新增的 2 个节点变"空闲"时，也会把它们移除。

> 💡 **AI Infra 视角**：这段日志完整展示了"Pod 弹性 → 节点弹性"的两级联动：HPA 先把 megapod 副本数从 1 扩到 2，但集群 GPU 已被占满，调度器报 `Insufficient nvidia.com/gpu`，Pod 卡在 Pending；Cluster Autoscaler 随即介入，把节点组从 2 台扩到 4 台。注意 Pending 状态对推理服务来说是"有损"的——新流量没有地方承接，所以生产上会配合就绪探针（readiness probe）把尚未就绪的副本从 Service 端点中摘除，避免请求打到没就绪的实例上。

## 8. （可选）NCCL Test

为了验证 EFA 是否正常工作，我们可以在节点之间运行一次 NCCL 测试。请务必修改 [nccl_test.yaml](./multinode_helm_chart/nccl_test.yaml) 文件，调整以下值：

- `slotsPerWorker`：设为集群中每个节点的 GPU 数量
- `-np`：设为"worker 节点数 × 每节点 GPU 数"
- `-N`：设为每节点 GPU 数
- `Worker: replicas`：设为测试要使用的 worker Pod 数量，必须小于或等于集群中的节点数
- `node.kubernetes.io/instance-type`：设为集群中要运行 nccl 测试的节点实例类型
- `nvidia.com/gpu`：设为集群中每个节点的 GPU 数量，在 limits 和 requests 两处都要修改
- `vpc.amazonaws.com/efa`：设为集群中每个节点的 EFA 适配器数量，在 limits 和 requests 两处都要修改

运行以下命令部署 NCCL Test manifest 所需的 MPI Operator：

```
kubectl apply --server-side -f https://raw.githubusercontent.com/kubeflow/mpi-operator/v0.5.0/deploy/v2beta1/mpi-operator.yaml
```

运行以下命令部署 NCCL test：

```
kubectl apply -f nccl_test.yaml
```

注意，launcher Pod 会持续重启，直到与 worker Pod 建立连接。运行以下命令查看 launcher Pod 日志：

## 9. （可选）GenAI-Perf

GenAI-Perf 是用于 Triton Server 的基准测试工具，用来衡量 LLM 的延迟和吞吐。我们在这里提供了一个示例。

### a. 修改 `gen_ai_perf.yaml` 文件

需要调整以下值：

- `image`：修改镜像标签。默认是 24.07，支持 TRT-LLM v0.11.0
- `claimName`：设为你的 EFS pvc 名称

### b. 运行基准测试

运行以下命令启动一个 Triton Server SDK 容器：

```
kubectl apply -f gen_ai_perf.yaml
kubectl exec -it gen-ai-perf -- bash
```

运行以下命令开始基准测试：

```
genai-perf \
  -m ensemble \
  --service-kind triton \
  --backend tensorrtllm \
  --num-prompts 100 \
  --random-seed 123 \
  --synthetic-input-tokens-mean 1024 \
  --synthetic-input-tokens-stddev 0 \
  --streaming \
  --output-tokens-mean 1024 \
  --output-tokens-stddev 0 \
  --output-tokens-mean-deterministic \
  --tokenizer hf-internal-testing/llama-tokenizer \
  --concurrency 1 \
  --measurement-interval 10000 \
  --url a69c447a535104f088d2e924f5523d41-634913838.us-east-1.elb.amazonaws.com:8001 \
  -- --request-count=10
```
